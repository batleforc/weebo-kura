---
title: Secrets, with or without Vault
description: The two ways kura-server gets its database, its bucket and the keys that encrypt every note — Vault (or OpenBao) on Kubernetes, or local files on a single host — and how to choose.
---

kura-server needs three secrets: the **database** URL, the **bucket**
credentials, and a way to protect each vault's **data key** (the AES-256 key
every chunk of the vault is encrypted with). It gets them in one of two
modes, set in `server.yaml`. A deployment uses one mode for its whole life.

| | Vault mode (`vault`) | Local mode (`localSecrets`) |
| --- | --- | --- |
| Where it fits | Kubernetes, with Vault or OpenBao | One host: the binary, or the image under podman or docker |
| Database URL | Vault KV (`vault.secrets.database`), re-read every 5 minutes; or `KURA_DATABASE_URL` | `KURA_DATABASE_URL` |
| Bucket credentials | Vault KV (`vault.secrets.bucket`), read at start | A JSON file (`localSecrets.bucketFile`), read at start |
| What wraps the data keys | One Transit key per tenant, `kura-<tenant>`, never leaving Vault | One master key file (`localSecrets.masterKeyFile`), held in the server's memory |
| Server login | Kubernetes auth (service account), or `KURA_VAULT_TOKEN` for local runs | None |
| Key rotation | Transit key versions (`rewrap`) | Not supported |
| Destroying a tenant's key after a purge | The operator deletes its Transit key | Nothing to destroy: the wrapped keys go with the purged rows |
| A restore needs | PostgreSQL, the bucket, and a Vault snapshot | PostgreSQL, the bucket, and the master key file |
| Stored data key | `vault:v1:…` (Transit ciphertext) | `kura-local:v1:…` |

Both modes encrypt the same way: each vault has its own data key, created
on first use, stored only wrapped in PostgreSQL, unwrapped into a cache of
at most 1,000 keys for 10 minutes. Only what wraps it differs.

## Vault mode

The default of the Helm chart, described step by step in
[Install](/docs/guides/install#prepare-vault).

```yaml title="server.yaml"
vault:
  address: https://vault.vault:8200
  kubernetesAuth: { mount: kubernetes, role: kura }
  secrets: { database: mv/data/kura/database, bucket: mv/data/kura/bucket }
  transit: { mount: transit }
```

- The server logs in with its service account and may only `datakey`,
  `decrypt` and `rewrap` with Transit: the key that protects the data keys
  never leaves Vault, and a stolen database dump is unreadable without
  Vault.
- One Transit key per tenant, created by an operator before the tenant's
  first vault (`vault write -f transit/keys/kura-<tenant>`).
- Rotating the database password needs no restart.
- When Vault is down, keys already in the cache keep working for up to 10
  minutes; then reads and writes of the vaults whose key is not cached
  answer `503`.

## Local mode

For a single host without Vault nor Kubernetes. Exclusive with `vault`.

```yaml title="server.yaml"
localSecrets:
  masterKeyFile: /etc/kura/master.key
  bucketFile: /etc/kura/bucket.json
```

```bash
umask 077
openssl rand -base64 32 > /etc/kura/master.key
cat > /etc/kura/bucket.json <<'EOF'
{ "endpoint": "https://s3.example.org", "bucket": "kura",
  "region": "us-east-1", "accessKeyId": "…", "secretAccessKey": "…" }
EOF
# Once, as the database owner (roles: see Install › Understand the database roles).
KURA_DATABASE_URL=postgres://kura_owner:…@db:5432/kura kura-server migrate
# Then the server, as kura_app.
export KURA_DATABASE_URL=postgres://kura_app:…@db:5432/kura
kura-server --config /etc/kura/server.yaml
```

- The master key is 32 random bytes in base64. It wraps every data key with
  AES-256-GCM, bound to the tenant's name: a wrapped key copied to another
  tenant's vault does not open.
- A master key of the wrong length, an unreadable file or a bucket file
  that is not the JSON above stops the server at start.
- Make both files readable by the server's user only (`chmod 600`), and
  mount them read-only in a container.

<Callout type="warn" title="The master key is every note">
Losing the master key loses every vault's data: nothing can decrypt the
bucket without it. Whoever holds it **and** a database dump and the bucket
can read every note. Keep a copy offline, apart from the database and
bucket backups, and never commit it.
</Callout>

## Choosing, and switching

Take the Vault mode when you already run Vault or OpenBao, or need key
rotation and a key that never sits on the server's disk. Take the local
mode for a home server or a single host where running Vault would cost more
than it protects.

A data key wrapped in one mode does not open in the other: the server
answers `503` for that vault, with a log saying which mode wrapped it.
Switching an existing deployment is not supported; to move, start a new
deployment in the other mode and push every vault again from a device
(`kura attach`, or the Obsidian plugin on a fresh vault).
